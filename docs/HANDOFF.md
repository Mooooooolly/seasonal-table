# 時令食材 App 交接說明

給 Claude Code 的建置說明。使用者 Molly,自用為主、之後可能公開。這份文件把已經決定的事、資料規則、要先驗證的風險都寫清楚,不確定的地方標成「待確認」,請不要自行假設。

## 1. 目標

手機優先的網頁 App:看北部批發市場的蔬菜價格與「當季」標籤,從食材找食譜、從食譜回推食材,並產生採買清單。第一版只做蔬菜,之後再擴到肉類、海鮮、蛋。價格是批發價,不是超市零售價,畫面上要註明。

## 2. 已決定事項

- 市場範圍(北部):台北一、台北二、板橋區、三重區、桃農,五個市場。
- 資料:農業部農產品交易行情,蔬菜類 `TcType=N04`。進口品種不排除,用 `is_import` 標示即可。
- 價格單位:元/台斤(600 公克)為主。資料原始單位是元/公斤,乘以 0.6。價格以區間顯示。
- 食材名稱:介面只用「群組名」(B 欄),不顯示市場品名(A 欄)。
- 佐料(蔥、薑、蒜頭、辣椒、香菜等)只供查價,不進主食材排名,也不算當季。
- 食譜只存食材、份量、佐料、器材、份數與原網址,不存作法步驟,不放照片。縮圖用主食材色塊加一個字。
- 器材選項:電鍋、炒鍋、湯鍋、烤箱、免開火。使用者可設定家裡有的器材,食譜頁預設只顯示做得出來的菜。
- 後台:使用者自己編輯「食材對照表」與「食譜」,新出現的未歸類品名與錯誤用畫面提醒,不發信也不推播。
- 後台資料庫:Supabase(已決定)。每天排程用 GitHub Actions,必要時改 Supabase 排程(見第 9 節)。

## 3. 資料來源 API 事實(已實測)

- 位置:`https://data.moa.gov.tw/api/v1/AgriProductsTransType/`
- 參數:`Start_time`、`End_time`(民國日期,例如 `115.10.22`)、`TcType=N04`、`MarketName`、`CropName`、`CropCode`、`Page`。
- 回傳:`{RS, Data[], Next}`。欄位:`TransDate`、`TcType`、`CropCode`、`CropName`(格式「品名-品種」,有些只有品名)、`MarketCode`、`MarketName`、`Upper_Price`、`Middle_Price`、`Lower_Price`、`Avg_Price`(元/公斤)、`Trans_Quantity`(公斤)。
- 單次最多 1000 列,`Page=2` 實測回傳空,所以不能靠分頁。必須縮小範圍:一個市場加一個日期視窗。台北一 3 天就約 692 列,所以每日更新用 1 天視窗。
- 一定要加 `MarketName` 篩選。同時送大量不篩選的請求,伺服器會變很慢。
- 資料約晚 4 天更新。最近一天可能只有部分市場。
- 休市日會回傳佔位列:`CropName="休市"`、`CropCode="-"`、數值全為 0。必須排除。也排除 `Trans_Quantity=0` 或 `Avg_Price=0` 的列。
- `data.moa.gov.tw` 的 robots 擋住網頁抓取工具。我當時是在同網域頁面內呼叫 API。伺服器端程式是否可直接呼叫、是否符合平台使用規範,**待確認**,見第 9 節。

## 4. 架構

- 每日排程 → 抓資料 → 寫入 Supabase 的 `raw_prices` → 重算 → 產出給前台的 `groups.json`、`recipes.json`。
- 前台是靜態網站(Netlify),只讀那兩個 JSON。
- 後台是同一個網站的 `/admin`,用 Supabase 登入,單一使用者。後台修改對照表或食譜後,可以按鈕觸發重算,每天排程也會重算。
- 對照表放資料庫的原因:使用者改 B 欄分類後,歷史資料要用新分類重算,所以原始資料一律以 A 欄(CropName)存,群組只在計算時套用。

## 5. 資料表(建議)

- `raw_prices`:`date`、`market`、`crop_name`、`crop_code`、`avg_price`、`upper_price`、`lower_price`、`qty_kg`。主鍵 `(date, market, crop_name)`。更新用 upsert。
- `crops`(A 欄):`crop_name`(唯一)、`crop_code`、`group_id`(可空)、`role`(`主食材`/`佐料`/`不適用(加工品)`/`不適用(非蔬菜或不明)`)、`confidence`、`is_import`、`note`、`status`(`mapped`/`unmapped`)、`first_seen`。
- `groups`(B 欄):`id`、`name`(唯一)。一個群組內的 A 欄角色要一致。
- `recipes`:`id`、`name`、`main_group_id`、`servings_text`、`equipment`(陣列)、`source_url`、`seasonings_text`、`notes`、`active`。
- `recipe_ingredients`:`recipe_id`、`order`、`name`、`qty_text`、`group_id`(可空,表示食材對得到哪個群組)。份量先存原文,不做數值化。
- `alerts`:`id`、`type`、`payload`、`created_at`、`resolved_at`。
- `group_stats`(計算結果):每個群組的價格區間、相對中位數百分比、當季旗標、近 30 天交易量、名次、前 10% 旗標,以及計算日期。

種子資料:`mapping.csv`(399 列 A→B,含角色與信心)、`recipes.json`(31 道食譜)。食譜裡的 `group` 是我用文字比對猜的(`group_is_guess=true`),後台要讓使用者確認或修正。

## 6. 計算規則

**資料範圍**:北部 5 個市場,排除休市與 0 值。

**週序列**:對每個 A 欄,依 ISO 週彙總。週加權均價 = Σ(Avg_Price × Trans_Quantity) / ΣTrans_Quantity(跨市場、跨日)。週交易量 = 日均交易量。

**A 欄當季判斷**:
- 現值:資料中最近 7 個有資料的日曆日(不是今天往回 7 天,因為資料有延遲)。
- 基準:過去 52 週(不含現值那週)有資料的週的中位數,價格與日均交易量各算一個。
- 當季 = 現值均價 < 價格中位數 **且** 現值日均交易量 > 交易量中位數。
- 資料不足:近 12 個月成交天數(市場日)少於約 60 的 A 欄,不判斷當季,也不參與群組投票。

**群組當季**:群組內「交易量(近 30 天)占一半以上」的 A 欄當季,群組才算當季。

**前 10% 與食譜範圍**:只在角色=主食材的群組中,依近 30 天交易量排名,取群組數的 10%(無條件進位)。第一版只替這批群組找食譜。目前排名為:高麗菜、白蘿蔔、大白菜、玉米、南瓜、小黃瓜、小白菜、絲瓜、紅蘿蔔、油麥菜、青花菜、地瓜、洋蔥、番茄。

**食譜當季**:主食材群組當季,或食譜裡「有追蹤價格的群組」有一半以上當季。完全沒有追蹤群組的食譜標示為不適用。

**價格顯示**:群組在最近 7 天內,各市場的加權均價,取各市場之間的最小與最大,乘以 0.6 換成元/台斤並取整。目前原型用的區間是示意值,正式版要改成這個算法。同時顯示「批發價・較近一年中位數 ±X%」,**不下「划算」之類的結論**。

> 注意:群組均價是把多個 A 欄混在一起算的,品種組成改變會讓均價變動(例如進口與國產價差大)。所以當季判斷在 A 欄層級做,群組均價只用來顯示。

## 7. 每日排程流程

1. 對最近 7 天、5 個市場各發一次 1 天視窗的請求,過濾後 upsert 進 `raw_prices`。
2. 發現 `crops` 裡沒有的 `crop_name`:新增一列 `status=unmapped`,並產生 `new_crop` 提醒。
3. 重算 A 欄當季、群組統計、前 10%、食譜當季。
4. 產出 `groups.json`、`recipes.json`。
5. 失敗(請求錯誤、資料量異常)或最新資料日期距今超過 7 天:產生 `job_failed` / `stale_data` 提醒。
6. **第一次執行要先補 12 個月歷史資料**:3 天視窗 × 5 市場,約 610 次呼叫,併發 4、遇錯重試加退避。我實測過這個做法可以完成,沒有失敗,約 6 分鐘。

## 8. 後台需求

登入後有四個頁面:
- **提醒收件匣**:未歸類新品名、食譜食材對不到群組、排程失敗或資料過期。有未處理數量的紅點。
- **食材對照表**:列出 A 欄,顯示群組名、角色、信心、進口標記、交易量、成交天數。預設先顯示未歸類與低信心的列。可改群組名(可新增群組)、改角色(下拉)。改完按鈕觸發重算。
- **食譜**:新增、編輯、停用。食材是一列一列的欄位,每列可選對應群組(自動完成,選項來自 `groups`)。器材多選。來源網址。可預覽前台長相。
- **群組總覽**:群組、角色、近 30 天交易量、名次、前 10% 標記、當季旗標。

## 9. 開工前先驗證的風險

1. **GitHub Actions 連不連得到 `data.moa.gov.tw`**:先建一個最小專案,寫一個排程工作呼叫 API 抓 1 天一個市場,看是否成功。連不上的備案:改用 Supabase 的排程函式或 Netlify 排程函式。
2. **平台使用規範**:確認農業資料開放平臺對程式化呼叫與重製的規範(政府資料開放授權),再決定要不要公開。
3. **排程被停用**:GitHub 對 60 天沒活動的專案會自動停用排程工作。要加保持活躍的機制,或把排程放在 Supabase。
4. **新品名處理**:未歸類的 `crop_name` 在使用者處理前,不得計入任何群組,也不得讓排程失敗。

## 10. 前台參考(看 `prototype.html`)

三個分頁:食材(預設首頁)、食譜、採買清單。

- 食材卡片:色塊、群組名、當季標籤、價格區間、「批發價・較近一年中位數 −20%」、食譜數。點進去彈出該食材的食譜。
- 食譜:搜尋食材或菜名、只看當季、器材篩選。食譜卡片顯示當季標籤與器材。點開後顯示食材與份量、佐料、器材、份數,下方有「加入採買清單」和「看原食譜」。
- 採買清單:每項食材一張卡片,**標題只顯示食材名稱**,份量不重複寫在標題;卡片裡每一行顯示「菜名標籤 + 份量」,同名食材合併。可勾選、可移除某道菜。第一版不自動加總份量,也不算總價。
- 清單與器材設定存在瀏覽器本機,不進資料庫。
- 原型的價格區間是示意值(均價上下 10%),當季判斷也是簡化版。這兩處要換成第 6 節的算法。
- 原型資料是我把試算表手動抄進程式裡的,正式版要改讀 `groups.json`、`recipes.json`。

## 11. 目前資料的已知事實

- 近 12 個月(2025-10-23 至 2026-10-22)北部 5 市場共有 399 個 CropName,已歸成 177 個群組。角色:主食材 325 列、佐料 51 列(含 13 列使用者要求從「待確認」改成佐料的)、不適用 23 列。
- N04 除了葉菜瓜果,還包含菇類、豆類、芽菜、筍類、根莖類與少數加工品。
- 市場品名常把不同用途放在同一名稱,所以才要以 A 欄為準再歸群組:例如「蘿蔔」含櫻桃蘿蔔與甜菜根、「玉米」含玉米筍、「萵苣菜」含多種萵苣、「絲瓜」含角瓜。
- 使用者已確認的歸類:花胡瓜=小黃瓜;敏豆=四季豆;本島圓葉與本島尖葉合併為「A菜」;荷蘭豆與甜豆分開。
- 信心標為「低」的歸類(約 47 列)使用者尚未逐項確認。
